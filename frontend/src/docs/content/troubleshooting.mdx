## Start with the desktop app

The desktop app owns the local daemon. First quit completely and reopen Tallpine, then confirm the project and selected session still appear. On macOS, use the menu-bar tray's **Quit Tallpine Completely** action for this restart. The app discovers or restarts its daemon and reconnects live event and terminal streams.

On macOS, closing the window or using **Quit / Cmd+Q** destroys the desktop window but leaves Tallpine in the Dock and menu-bar tray. Its daemon and enabled mobile/remote access keep running while the Mac stays awake and reachable. Click the Dock icon or **Show Tallpine** in the tray to reopen the window. Existing unsaved-draft warnings still apply; desktop browser previews and browser automation stop until the window reopens. Windows and Linux quit behavior is unchanged.

If you use the optional CLI, `tallpine status` and `tallpine doctor` provide additional local diagnostics:

```bash
tallpine status
tallpine doctor
tallpine doctor --json
```

`tallpine doctor` checks daemon/config state, the data directory and database, Git, and tmux on macOS/Linux. It is not required for a normal desktop-only install.

## Desktop and daemon

<Accordions>
	<Accordion title="The app opens but no projects appear">
		Confirm you opened the expected Tallpine data home. All state defaults under `~/.tallpine`; an `TALLPINE_DATA_DIR` or `TALLPINE_RUN_FILE` override can point a development launch at a different daemon instance.
	</Accordion>
	<Accordion title="The CLI says the daemon is not running">
		Open the desktop app first. Product CLI commands are thin clients and need the app-owned daemon. A stale `~/.tallpine/running.json` is not enough; Tallpine also verifies the recorded process.
	</Accordion>
	<Accordion title="The daemon port is occupied">
		Where the daemon uses loopback TCP (Windows, or when the Unix socket is unavailable), it binds port `3101` by default and fails fast if it cannot bind. On macOS and Linux, a stale `sock/daemon.sock` from a crashed daemon is removed at the next start. Stop the conflicting local process or use a deliberate development `TALLPINE_PORT` override. Never change the bind host to expose the daemon.
	</Accordion>
	<Accordion title="The UI looks stale after a daemon restart">
		Leave the app open briefly so its SSE connection can reconnect and invalidate current queries. If it does not recover, restart the desktop app. The event stream supports replay, but a full app restart is the safest user-level recovery.
	</Accordion>
</Accordions>

## Agents and sessions

<Accordions>
	<Accordion title="No agent harness is offered">
		Install the harness, run it once to authenticate, and restart Tallpine. The desktop daemon inherits a login-shell environment and reuses each provider's installed binary and authentication.
	</Accordion>
	<Accordion title="Chat preflight fails">
		Confirm the selected harness supports native Chat and its binary is authenticated. Chat support depends on the harness and installed version; see the [agent capability catalog](/plugins/agents#chat-versus-terminal-ui). Check **Settings → Harness** and provider version/permission requirements. Choose Terminal UI when the harness lacks Chat support or preflight cannot connect.
	</Accordion>
	<Accordion title="A TUI session will not start on macOS or Linux">
		New macOS/Linux sessions use detached native PTY hosts. Packaged builds bundle tmux for old sessions/fallback; macOS still validates it. For source runs check configured/system tmux and the native-host launch error. Windows uses ConPTY. See [Runtime](/plugins/runtimes).
	</Accordion>
	<Accordion title="The session is blocked">
		Open the session and answer the pending approval or permission prompt. Tallpine deliberately does not inject lifecycle messages while a controller is blocked.
	</Accordion>
	<Accordion title="The status appears wrong">
		Status is derived from activity, termination, controller, and pull-request facts. A failed runtime probe is not treated as death. Reopen the session and inspect its Chat or terminal before killing it.
	</Accordion>
	<Accordion title="A session will not restore">
		Use the desktop restore action or `tallpine session restore <session-id>`. Restore reuses the same session and worktree when the selected adapter supports recovery. Check that the harness remains installed and authenticated. For a stopped controller on a non-terminated session use `tallpine session resume-agent <id>` instead. A disabled interface switch can indicate unavailable native history, an unsupported direction, or pending recovery; inspect its reason before retrying.
	</Accordion>
</Accordions>

## GitHub and pull requests

<Accordions>
	<Accordion title="Repository or pull-request data is missing">
		Run `gh auth status` and confirm the active account can access the repository. GitHub authentication is lazy so an auth failure does not need to block unrelated local session work. For GitLab check token/`glab` authentication and self-managed-host configuration in [SCM setup](/plugins/scm).
	</Accordion>
	<Accordion title="The agent opened a PR but Tallpine did not link it">
		Claim it from the session UI or, inside the worker, run `tallpine session claim-pr <pr-number-or-url>`; Tallpine reads the worker from `TALLPINE_SESSION_ID`. From another shell, use `tallpine session claim-pr <session-id> <pr-number-or-url>`.
	</Accordion>
	<Accordion title="CI or review data is delayed">
		The SCM observer polls GitHub and respects rate limits and ETags. Check `gh auth status`, wait for another observation cycle, and open the pull request directly for full raw logs or comment bodies.
	</Accordion>
	<Accordion title="Review findings were not sent to the worker">
		Open the review run and use its send action. Reviewer execution and delivery are separate operations so you can inspect findings before changing the worker conversation.
	</Accordion>
</Accordions>

## Browser preview

<Accordions>
	<Accordion title="The Browser tab is blank">
		Select a target explicitly with `tallpine preview <url>`, or use `tallpine preview start` when the worktree contains a valid `.tallpine/launch.json`. Tallpine does not auto-discover a preview for every new worker.
	</Accordion>
	<Accordion title="A configured preview server will not start">
		Run `tallpine preview start <configuration>` and inspect the returned error. Verify the command and working directory in the session's `.tallpine/launch.json`, then run the same command in its worktree shell.
	</Accordion>
	<Accordion title="Browser automation targets the wrong page">
		Select the correct session and browser tab. Commands are authorized for the selected session. Temporary profiles are isolated; named profiles deliberately reuse saved browser state. Check the selected profile, and refresh snapshots after navigation. Keep the panel visible for screenshots/human pointer actions. Profile imports have platform-dependent cookie support; a missing login may require signing in again.
	</Accordion>
</Accordions>

## Connections

<Accordions>
	<Accordion title="The phone cannot connect">
		Confirm Connections is enabled and the QR is ready, then scan a fresh QR code; pairing codes work once. On the same Wi-Fi the phone uses the local address; away from home, use Tailscale or the optional Cloudflare quick tunnel. Update both apps for identity or version mismatches. A phone paired before HTTPS must pair again.
	</Accordion>
	<Accordion title="The QR code was shared">
		The QR carries the computer identity, its addresses, the certificate pin and a one-time pairing code. Do not share it. If it was used by someone else, unpair that phone in Connections.
	</Accordion>
	<Accordion title="Can I use Connections on public Wi-Fi?">
		Yes. The phone talks to the Mac over HTTPS and pins its certificate, so the network cannot read or impersonate the connection. This does not hold for the optional Cloudflare quick tunnel: Cloudflare can read that traffic. The Mac must still be reachable, for example over Tailscale. See [Connections](/configuration/remote-access). If mobile push is missing, check phone notification permission, that the phone is still listed under Phones that can control this Mac, and daemon connectivity.
	</Accordion>
</Accordions>

## Still stuck

| Symptom | Where to go |
| --- | --- |
| macOS Gatekeeper says the developer cannot be verified | Follow the Gatekeeper steps in [Common Installation Problems](/installation#common-installation-problems). |

Open an issue in the [Tallpine repository](https://github.com/justvibedev/tallpine/issues). Include the desktop version, operating system, agent harness and interface mode, reproduction steps, and sanitized `tallpine doctor --json` output when the CLI is available. Never attach credentials, provider transcripts, or the entire `~/.tallpine` directory.
